# codeplan

English · [한국어](README.ko.md)

codeplan keeps a plan of a repository beside its code and writes a page that
shows the parts, which parts use which, and scenarios through them. The page
also lists the tasks written in the plan, each with its status and how many
of the files it is to make are there. Once the plan file is out of date, the
`check` command exits non-zero. `check` can run in CI, where it stops a pull
request, or without CI, from a pre-push hook or on a schedule.

The plan has two kinds of content. Written by people: the repository split
into parts, with a name and a description for each, which parts use which,
the outside systems they use (externals), scenarios that follow one
request through the parts, and tasks: units of work with a status and the
files each is to make. Counted by the tool: the files and lines each
part owns, from glob patterns in the plan file. From both, codeplan writes a
single HTML page that draws the parts and lets a reader step through a
scenario.

`check` fails when a watched file belongs to no part, when two parts own the
same file equally, when code sits outside the watch set, when the plan file
has an error, or when the page no longer matches the plan file and the code.
When `check` runs in CI, the plan is reviewed in the same pull request as
the code that changes it.

codeplan works with JavaScript and TypeScript, and with Java and Kotlin
(including MyBatis mapper XML). It is one file, `codeplan.mjs`, that needs
only Node 22 or later; nothing is installed into the repository's
dependencies.

The idea was inspired by almendili's architecture-map.

## Quick start

In the repository to plan, with this repository checked out at
`/path/to/codeplan`:

```sh
mkdir -p docs/codeplan
cp /path/to/codeplan/skill/codeplan/codeplan.mjs docs/codeplan/codeplan.mjs
node docs/codeplan/codeplan.mjs draft > codeplan-draft.json
node -e '
const fs = require("fs");
const draft = JSON.parse(fs.readFileSync("codeplan-draft.json", "utf8"));
const config = fs.existsSync("codeplan.json") ? JSON.parse(fs.readFileSync("codeplan.json", "utf8")) : {};
for (const key of ["languages", "watch", "roots"]) delete config[key];
fs.writeFileSync("docs/codeplan/plan.json", JSON.stringify(draft.plan, null, 2) + "\n");
fs.writeFileSync("codeplan.json", JSON.stringify({ ...config, ...draft.config }, null, 2) + "\n");
'
rm codeplan-draft.json
node docs/codeplan/codeplan.mjs update
node docs/codeplan/codeplan.mjs check
```

`draft` proposes parts from the directories (and, in Java, from modules and
packages) and prints a plan file and a config file. Between `draft` and
`update`, give the parts names and descriptions in `docs/codeplan/plan.json`
and add `uses`, externals and scenarios; see the
[plan file reference](skill/codeplan/docs/plan-file.md). Then open
`docs/codeplan/codeplan.html` in a browser.

`node docs/codeplan/codeplan.mjs summary` prints the same plan as Markdown
with a mermaid diagram, for a pull request or a README.

## Files to commit in the planned repository

| File | What it is |
|---|---|
| `docs/codeplan/codeplan.mjs` | the tool |
| `docs/codeplan/plan.json` | the plan file |
| `codeplan.json` | the config file (optional when the defaults fit) |
| `docs/codeplan/codeplan.html` | the page |

The page is generated by `update`, but `check` compares it byte for byte
with what `update` would write, so it is committed too. It holds no time and
no absolute path, so every machine writes the same bytes.

## In CI

```yaml
name: codeplan
on:
  pull_request:
  push:
    branches: [main]
jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v7
      - name: Set up Node
        uses: actions/setup-node@v7
        with:
          node-version: 22
      - name: Check the plan
        run: node docs/codeplan/codeplan.mjs check
```

Exit code 1 means the plan is out of date with the code: there are orphan,
contested or unwatched files, a warning in the plan file, or a page that
`update` would change. Run `update`, fix the listed problems and commit.
Exit code 2 means the config file or plan file cannot be used, or the plan
file has an error.

For pull requests, `report` writes what state the plan is in and which
parts the pull request changed, as Markdown for the job summary. The
workflow for it is in the [CI reference](skill/codeplan/docs/ci.md).

## Without CI

Where there is no CI, or you cannot change it, nothing stops a pull request
whose plan is out of date. `check` can still run from a pre-push hook in
your own clone or on a schedule, and `update` and `summary` need neither.
A script on a schedule can keep one record of each run, and `history` makes
one HTML file from those records.
See the [reference for use without CI](skill/codeplan/docs/without-ci.md).

## As a Claude Code skill

`skill/codeplan` is a skill folder: `SKILL.md` tells an agent how to make
and keep a plan, and `codeplan.mjs` is the tool it copies into a repository.
Copy or link the folder into a skills directory, for example:

```sh
cp -R /path/to/codeplan/skill/codeplan ~/.claude/skills/codeplan
```

## Known limits

- The lines between parts are the uses people wrote in the plan file.
  `check` does not look for uses in the code that the plan leaves out.
- A scenario is stepped through by hand; there is no automatic playback.
- The theme choice is kept per browser, not in the page.
- A file whose name contains a backslash cannot be written as a `start`.
- `draft` reads `roots` from the config file only as plain paths, not as
  globs.
- The page loads nothing from outside and holds no absolute path or time.

## Developing codeplan

```sh
npm ci
npm run typecheck
npm test
npm run build
```

`npm run build` writes `skill/codeplan/codeplan.mjs`; CI checks that the
committed file matches a fresh build byte for byte (`npm run check:bundle`).
